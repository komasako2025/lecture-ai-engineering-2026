- 取り組んだレベル：基礎 
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を初期値の `5` から `1` に変更し、検索時にモデルへ渡す上位ページ数を1件に絞った。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
  - モデル：`gemini-3.5-flash-lite`
  - 対象資料：第1〜3回本講義（214ページ）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
| 項目 | 変更前（`RAG_TOP_K = 5`） | 変更後（`RAG_TOP_K = 1`） |
| :--- | :--- | :--- |
| 回答の正しさ | 正答（LoRAの固定・学習対象、QLoRAの4bit圧縮を正確に説明） | 正答（同じ内容を正確に説明） |
| 引用根拠 | 第2回・PDF p.51, p.52 | 第2回・PDF p.52 のみ |
| `--trace` 出力（ツール呼び出し） | `search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回実行（モデル応答 2 回） | `search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回実行（モデル応答 2 回） |
| 時間（秒） | 13.12 秒 | 2.57 秒 |
| トークン数（入力／出力） | 3,027 tokens ／ 225 tokens | 1,189 tokens ／ 195 tokens |
| 生成API推定費用（USD） | $0.001471 USD | $0.000844 USD |
- 改善した例と、残る失敗・制約：
  - 改善した例：検索件数を1件に絞ったことで、入力トークン数が約6割削減（3,027 → 1,189 tokens）され、生成API推定費用も約43%削減（$0.001471 → $0.000844）された。また、引用根拠も最も関連度の高い p.52 のみに絞られた。
  - 残る失敗・制約：今回は単一ページ（p.52）に答えが完結している質問だったため `RAG_TOP_K = 1` でも正答できたが、複数ページに根拠が分散している質問では情報が欠落する制約がある。
- 気づき・疑問：
  - 気づき：1ページに情報がまとまっている質問であれば、取得件数を増やすよりも少なく絞る方がトークン数・コスト・引用の明確さの面で有利になることが実測で確認できた。
  - 疑問：複数ページにまたがる質問を `RAG_TOP_K = 1` の状態で投げた場合、エージェントは1回目の検索結果を見て情報不足と判断し、検索クエリを変えて自動で再検索を行うのかが気になった。
